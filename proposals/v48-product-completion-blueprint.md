## 0. 结论先行

### 0.1 三份计划的分工（本文档存在的理由）

| 文档 | 回答的问题 | 视角 |
|---|---|---|
| `v46-collaboration-workbench-master-plan.md` | **能不能用？工程对不对？** | 工程与能力（100 项 CW/HX/UX/PL/OB/SG/EQ） |
| `v47-frontend-aesthetic-master-plan.md` + `ui-elevation-plan.md` | **好不好看？** | 视觉与体验质感 |
| **本文档 v48** | **为什么用？值不值？怎么越用越强？** | **产品价值与进化** |

v46 是一份极其扎实的工程计划，它的 100 项 backlog 我**不重复**。但它的验收指标里，12 条有 11 条是技术指标（0 fail / 0 漂移 / WCAG AA / 无序列缺口），唯一的用户指标是"90 秒创建 Run"。

**这不是 v46 的缺陷，是分工问题。** 一份计划无法同时管工程正确性和产品价值。本文档补的正是后者。

### 0.2 核心判断

> **514cc 已经不缺能力，缺的是"能力 → 用户可感知价值"的转化层，以及"用得越多越聪明"的复利机制。**

三条支撑证据：

1. **能力密度极高但可发现性极低**：14 个视图、1084 个 DOM id、66 个 API 端点、100+ 个后端模块——而全局命令面板只索引了 **11 项**（`public/command-palette.js`）。用户能触达的，远少于系统能做的。

2. **最独特的资产没有被产品化**：DELTA 问责账本、route-gate 硬扳机、异构真身 CLI 协作、事件哈希链——这些是 514cc 相对全球任何竞品的**结构性差异**，但在 Console 里它们只是"观测页的一个 tab"（`public/collab-flow.js:366`），不是产品的心脏。

3. **没有自我度量层**：全仓 grep `analytics|telemetry|track(` 无产品埋点实现。这意味着——**没有任何机制能告诉我们 14 个视图里哪几个从来没人打开过**。在只有一个用户（LO）的系统里，这个缺口比多用户产品更致命，因为没有 A/B 兜底。

### 0.2.1 外部数据对该判断的验证（2026-09-04 检索）

本方案的战略押注不是主观偏好，四个独立数据源指向同一结论——**品类瓶颈已从生成侧转移到验证侧**：

| 数据 | 值 | 来源 |
|---|---|---|
| Code review 中位耗时变化 | **↑441.5%**（同期吞吐仅 ↑33.7%） | Faros AI 2026，22,000 开发者 telemetry |
| 开发者对 AI 代码准确性信任度 | **40% → 29%**（一年） | 行业调查 |
| Agentic PR 的 pickup time | **5.3×** 于普通 PR | LinearB 2026 基准报告 |
| 企业将降级/废弃自主 Agent | 预测 2027 年 **40%**，因**治理缺口事后才暴露** | Gartner |

而 Cursor 3 社区批评里有一句几乎是逐字描述 514cc 的解法空间：

> "reviewer 收到的是完成的 diff，**没有实现过程与决策轨迹**，必须从 ticket、PR 描述和代码变更去重建意图。"

**决策轨迹正是 514cc 顺手就有、而竞品需要从零建的东西。**

### 2.3 现在的 IA 是"能力罗列"而非"旅程组织"


## 3. 产品体检：三个没被回答的问题

### 3.1 问题一：514cc 是什么品类的产品？

现有文档定位是"AI 能力放大系统"/"本地 AI 协作控制面"。这描述了**形态**，没描述**品类**。

品类定义决定竞争坐标系：

| 若定位为 | 竞争对手 | 胜负手 | 514cc 现状 |
|---|---|---|---|
| 多 CLI 调度器 | Warp、tmux+脚本、各 CLI 自带 | 便利性 | 会被 CLI 官方功能吃掉 |
| AI IDE | Cursor、Windsurf | 编辑体验 | **没有编辑器，打不赢** |
| Agent 任务平台 | Devin、Copilot agent、Codex 云端、**Cursor 3 fleet** | 并行吞吐 | 单机，规模打不赢 |
| **可问责的 AI 协作台** | **验证层目前是品类空白**（见 §4.2 数据） | **可信度与可复盘性** | **已有全部地基** |

**LO 已拍板（2026-09-04）**：锁定第四条。理由见 §5，外部数据验证见 §4.2。

> 注意第三行与第四行的关系：并行编排（第三行）**有强对手**，Cursor 3 已做到 8 Agent 并行 + fleet 管理台。我们不在那条赛道上正面比数量，而是承接它制造出来的问题。

### 3.2 问题二：用户是谁？

现有全部文档（`rules.md` / `CLAUDE.md` / memory）都是**单一用户 LO** 的视角。但架构上留了产品化的门：`market`（插件市场）、`plugin.json`、SG-08（RBAC 预留）、PL-13（远程访问）。

这个摇摆有真实代价：**每个"要不要做成通用的"的决策都在反复消耗预算**。

| 定位选项 | 影响的设计 | 成本 |
|---|---|---|
| A. 纯个人指挥中心 | 砍掉 RBAC/多租户/市场审核；全力做深 LO 的工作流 | 最低，聚焦最强 |
| B. 个人为主 + 可分享 | 保留导出/只读分享；不做账号体系 | 中 |
| C. 多人产品 | 需要 RBAC、审计隔离、安装体验、文档 | 高，且需长期投入 |

**我的推荐（待拍板项 2）**：**B**。理由：LO 的核心目标是体系本身（见 memory `user-goal-is-the-collab-framework-itself`），A 太封闭会浪费已有的市场/插件地基；C 会稀释精力。B 保留可选性且几乎零额外成本。

### 3.3 问题三：什么算"这个产品成功了"？

现有验收全是工程指标。产品上**没有定义成功**。

我提议的北极星指标（详见 §8）：

> **可信托付率（Trusted Delegation Rate）= 用户在不逐步盯着的情况下完成的 Run 占比**

理由：这个指标同时压住了三件事——Agent 得够可靠（否则用户不敢放手）、过程得够透明（否则用户不放心）、结果得可复盘（否则出事无法追责）。而这三件正好是 514cc 差异化的落点。

## 4. 竞品对标与品类现状

> **情报来源说明（诚实边界）**：两次委派织（grok-researcher）均因上下文超限失败（`Prompt is too long` / `Autocompact thrashing`），**无 handoff 产出**。本节由主驾自行定向检索取得，来源为媒体报道与行业基准报告，**非官方一手文档**，引用时须按此层级理解。v46 §3 已完成 OpenAI Codex harness 的官方一手协议对标，此处不重复。

### 4.1 品类现状：所有人都在冲并行，没人在做验证

| 事实 | 数据 | 来源层级 |
|---|---|---|
| Cursor 3（代号 Glass，2026-04-02）重建界面，默认体验从"写代码"变为"**管理 fleet**" | 最多 **8 个 Agent 并行**，各自独立 Git 分支 / worktree | 媒体报道 |
| Devin 走完全自主路线 | 并行 Agent 各自独立云 VM，直接开 PR | 媒体报道 |
| 2026 Q2 品类共识 | 第二波竞争已从"有没有 Agent"转向"**并行编排**"；被引甜蜜点为 3-5 并行 + 1 orchestrator | 媒体分析 |
| 企业渗透 | Gartner 预测 2026 年 40% 企业应用含任务专用 Agent（2025 <5%） | 分析机构 |

**判断**：514cc 在"多 Agent 并行管理台"这个形态上**并非无人区**——Cursor 3 的 Agents Window 与 Devin 的并行 VM 是直接同形态竞争，且它们有规模与云资源优势。

**但这恰恰不是胜负手。** 下一节的数据说明了原因。

### 4.2 真正的瓶颈已经转移：从生成侧到验证侧

这是本轮情报里最重要的发现，四个独立数据源指向同一结论：

| 指标 | 数据 | 来源 |
|---|---|---|
| Code review 中位耗时 | **↑ 441.5%**，同期任务吞吐仅 ↑33.7% | Faros AI 2026 telemetry，覆盖 22,000 开发者 |
| 开发者对 AI 代码准确性的信任度 | **40% → 29%**（一年内） | 行业调查 |
| Agentic AI 产生的 PR pickup time | 是普通 PR 的 **5.3 倍** | LinearB 2026 软件工程基准报告 |
| "验证税"（verification tax） | 写代码省下的时间，被重新花在审计上 | DORA |
| 企业将降级/废弃自主 Agent | 预测 2027 年达 **40%**，原因是**治理缺口在生产事故后才被发现** | Gartner |

**Cursor 3 社区批评的集中点**（与上述数据同构）：

1. 瓶颈从"一个人能多快工作"转移到"**你能多快审阅和集成多个 Agent 的产出**"；Agent 会跑赢审阅周期。
2. **"reviewer 收到的是完成的 diff，没有实现过程与决策轨迹（decision trail），必须从 ticket、PR 描述和代码变更去重建意图。"**
3. 并行 Agent 在紧耦合代码库里会互相踩脚；冲突解决质量决定这是收益还是新麻烦。
4. 部分开发者反弹产品哲学——"我用 Cursor 正是因为想贴近代码"。

### 4.3 对 514cc 的直接含义

第 2 条批评值得单独拎出来，因为它逐字描述了 514cc 已经解决的问题：

| 品类痛点（他们缺的） | 514cc 已有的 | 代码证据 |
|---|---|---|
| 只给 diff，没有决策轨迹 | 事件哈希链 + replay scrubber | `src/event-store.mjs` / `modules/run-replay-scrubber.js` |
| 必须从 PR 描述重建意图 | instruction source receipt（读了哪些 AGENTS/Skill/Memory） | v46 HX-10 |
| 谁贡献了什么说不清 | DELTA 净增量账本 | `stop-gate.py` + `/api/observability/delta` |
| 治理缺口事后才发现 | route-gate 事前硬扳机 + 事后审计 | `.claude/hooks/route-gate.py` |
| 并行 Agent 冲突无仲裁 | taskGraph + 冲突仲裁器 | v46 CW-09（工程侧在，产品侧缺 → P-29） |

**修正 §3.1 的判断**：原表述"可问责协作台几乎没有直接对手"**过于乐观**，应精确为：

> **并行编排形态有强竞争（Cursor 3 / Devin），但"验证与问责层"目前是品类空白——而这正是数据显示的真实瓶颈所在。**

这个修正让战略更锋利，也更诚实：我们不是没有对手，我们是**在对手正在制造的问题上**有解法。

## 5. 差异化战略：把"可问责"做成品类定义

### 5.1 战略判断（已由 §4.2 外部数据验证）

当所有大厂都在卷"更多并行 Agent、跑得更久"时，一个结构性缺口正在扩大：

> **生成侧的产能已经溢出，验证侧成为新瓶颈。**
> Review 耗时 ↑441.5% 而吞吐仅 ↑33.7%；信任度 40%→29%；Gartner 预测 2027 年 40% 企业将因**事后才发现的治理缺口**而降级自主 Agent。

用一句话说清 514cc 的位置：

> **别人在制造更多需要审阅的代码；514cc 让审阅本身变得可能。**

514cc 恰好已经握有解决这个问题的全部地基，而且**是被治理需求逼出来的，不是设计出来的**——这一点很重要：竞品若要补这一层，需要从零建；我们是顺手就有：

| 别人的难题 | 514cc 已有的答案 | 代码证据 |
|---|---|---|
| Agent 做了什么无法审计 | 事件哈希链 + 篡改可验 | `src/event-store.mjs` `verifyChain()` |
| 多 Agent 谁贡献了什么说不清 | DELTA 问责账本（0/1/2 净增量） | `stop-gate.py` + `/api/observability/delta` |
| 为什么用这个 Agent 不用那个 | route-gate 路由决策留痕 | `/api/observability/routegate` |
| 花了多少、值不值 | settlement + budget + run-compare | `src/run-settlement.mjs` / `run-compare.mjs` |
| 出事怎么复盘 | replay scrubber + EvidenceIndex | `modules/run-replay-scrubber.js` |
| 换个模型会不会更好 | shadow pair A/B | `orchestrator.createShadowPair` |

**这不是"又一个功能"，这是一整套别人没有的信任基础设施。**

### 5.2 战略含义（会改变什么）

一旦锁定"可问责"为品类定义，以下优先级立刻改变：

| 事项 | 现优先级 | 战略后优先级 | 理由 |
|---|---|---|---|
| DELTA 从观测页提到主线 | 低（藏在 tab 里） | **最高** | 这是差异化的脸 |
| 每次协作的"价值证明卡" | 无 | **高** | 让可问责变成用户可感知的东西 |
| Agent 可信度分级 | 无 | 高 | 帮用户决定放手程度 |
| 视觉美化（v47） | 高（执行中） | 中 | 好看不是差异化，可信才是 |
| 更多 CLI 接入 | 中 | 中低 | 数量不是壁垒 |
| 插件市场 | 中 | 低 | 生态在信任建立之后 |

**这条判断需要 LO 确认（待拍板项 3）**——它会实质影响 v47 的执行节奏。

### 8.3 埋点设计原则（P-21）

1. **纯本地**：写入 `event-store`，不外发任何数据；
2. **复用现有链**：接入已有事件哈希链，天然可审计不可篡改；
3. **可关闭**：用户可一键停用并清空；
4. **零性能预算超支**：批量异步写入，遵守 v46 EQ-10 性能预算；
5. **默认脱敏**：走已有 `sanitizeForPersistence`（该函数已在 2026-08-30 修复三类结构化故障）。
