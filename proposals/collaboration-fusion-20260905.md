# 协作工作面融合架构

日期：2026-09-05。本文是 `product-experience-reframe-20260905.md` 的 B 阶段深化，不新增竞争路线图。LO 明确要求体系融合、合理布局、深度重构和保留既有功能。

## 方向取舍

| 唯一主心智模型 | 适用性 | 决定 |
|---|---|---|
| 对话主导 | 单成员聊天顺手，但容易把项目执行、责任和成果降为附件 | 保留私聊能力，不作为整体架构 |
| 项目主导 | Project 定义工作范围，Conversation 持续承载目标，Run 表达本次执行 | 采用，与服务端真源和已有能力匹配 |
| 任务交付主导 | 有利于交付审阅，但新增 Task 身份会与现有 Conversation/Run/taskGraph 重叠 | 作为同一工作对话的过程/成果视图，不再造任务数据库 |

因此，“融合”不以页面数量或菜单互相跳转衡量，而以同一身份、同一命令准入、同一事件来源和相互一致的状态为依据。

## 对象与责任

| 对象 | 职责 | 不承担的职责 |
|---|---|---|
| Project | 持久化目录、项目归属、默认协作室与项目任务 | 不等于一次运行，也不因零成员/零消息而无效 |
| Conversation | 持续的工作对话、成员名单、Run 链 | 不以 UI 页签或原生 CLI session 代替 |
| activeRunId | 服务端决定当前消息准入与执行归属 | 不由历史浏览选择覆盖 |
| selectedRunId | 查看当前或历史执行的偏好 | 不决定发送、停止的目标 |
| 成员 | 可见协作身份与绑定的运行席位 | 不把成员页等同于独立任务 |
| coordinator / executionOwner | 协调责任 / 执行责任，可由同一成员承担 | 不能只按头像、页签或列表顺序推断 |
| taskGraph / delegation | 服务端登记的任务与委派证据 | 不是完整审计历史，也不自动证明目标完成 |

私聊仍绑定一位成员；项目对话仍采用持久化群聊契约。直接收件人当前最多一位，这是 `normalizeConversationRecipientIds()` 的明确约束。没有显式收件人时由现有团队编排处理，不能把 `@成员`、项目 roster 和首轮 fan-out 上限混为一谈。

## 本轮已实现

### 一个操作宿主

`#bot`、`#conversation=` 与 `#experience` 进入同一 `#view-bot` DOM 和 Bot 业务状态。移除 B1 独立展示循环，保留 B1 的 URL/归属解析兼容。没有第三份项目索引、执行队列或重复 composer。

项目与对话树、精确项目筛选、隐藏/删除记录、创建与成员目录在左侧。中央的对话、过程、成果共享同一输入节点；审批与待回答共用输入上方的待处理区域。当前执行与历史查看有明确区别。高级 Workbench、终端、配置、自动化、记录和其他工具继续可达。2026-09-06 补充：依 LO 后续授权及 D-2026-09-05-005，默认入口已切为 Bot，experience 不再有独立可见入口。

### 独立的对话准入命令

普通持久化 Conversation 消息经 `conversation-commands.js` 直接调用现有 `/api/conversations/:id/messages`。不再改写隐藏 Workbench 输入框、清空其选中 Run，或通过 `requestSubmit()` 借用另一表面的状态。

命令冻结 Conversation、文本、收件人、附件与新 Run 权限；按 Conversation 防重复准入，不阻塞其他对话。15 秒超时释放本地锁、保留草稿并明确未知结果，不自动重发。有效服务端回执与后续界面刷新分开，刷新失败不能抹掉已经受理的事实。

Ask 回答、恢复确认和部分原生命令目前仍复用旧的专用桥接链，不能把普通发送的独立化宣称为所有命令都已抽取完毕。

### 选择与草稿

`conversation-workspace.js` 只持有视图/草稿偏好，领域数据仍来自现有服务端索引与共享 Run 投影。历史请求沿 selection epoch 拒绝晚到覆盖；消息同步继续检查 Conversation、Run、generation 和 store key。

草稿按 Conversation 单独写 sessionStorage，兼容旧 v1 草稿，不截断或逐出未发送文本。配额不足时保留内存并显示本页暂存状态。首次建立 Conversation 迁移原文本；成功提交按原 owner 与文本快照消费，不能误清另一对话或新输入。IME 确认 Enter 不提交。

### 可控的渲染成本

统一工作面使用现有消息投影和实时增量组件，不再只读 `run.messages`。持续事件采用有界节流；增量 DOM 保留静态消息、展开状态和输入节点。

- 对话索引每页最多 100 条记录，空项目也可通过分页访问。
- 消息窗口最多 160 条消息，可前后分页与回到最新；上翻时冻结消息锚点。
- 过程面任务与委派分别每页 50 条，不按当前服务端上限一次性挂载。
- 私聊实时增量限定绑定成员；历史 Run 仍经过 Conversation 归属校验。
- 旧 Workbench 修复团队窗口 `all/team` 键不一致，以及达到 48 条后禁用纯 delta 快速路径的问题。未宣称旧渲染器已全部改造成增量框架。

### 协作成员闭环

当前项目工作对话有独立成员编辑器，使用既有 PATCH 与 revision CAS。允许空团队草稿；非空团队需要可协调成员。已知运行中/只读状态禁止编辑。保存后服务端清空当前 Run 引用，历史 Run 与原成员快照保留；后续消息由新成员名单建立执行上下文。冲突不自动覆盖。

这不是远端强事务的新实现：服务端更新、归属和版本号规则保持原状。浏览器验收证明了真实 PATCH、历史保留与并发冲突拒绝。

## 完成与权限

运行结束不等于目标验收。新主面展示“运行结束”与待确认的成果验收；控制中心全局 DELTA/handoff/发布记录单列为控制中心审计，不充当当前 Run 的专属证据。

新输入区默认显式发送 `plan`，可为新 Run 选择受控 `build`。当前 Run 的权限仍来自真实快照，运行中不把新控件伪装成即时调参。模型/effort 与原生权限的完整控制仍保留在既有席位及高级运行工具，尚未完成统一命令抽取。

已知契约分歧：`conversations-http.test.mjs:191` 明确请求 `build`，`:200` 仍要求强制 `plan`；开工前已有的 `orchestrator.mjs` 改动允许显式权限及继承部分运行配置。此次没有改动该服务端逻辑，也没有改测试期待值。需要单独统一“新 Run 重建权限”和“用户显式权限选择/配置继承”的合同，并覆盖审批、lease、原生 override 与预算边界。

## 验收与后续

本轮通过隔离服务、合成准入响应、真实浏览器 SSE、真实成员 PATCH/CAS 和 focused 测试验证。合成准入响应对应服务端持久化的 `execute:false` Run，不是模型执行证明。模型生成、真实 provider/SSH、正式 Tauri 激活和发布均未验证。

继续顺序：先统一权限与配置继承合同，再抽取 Ask/恢复/原生命令的剩余桥接；阶段 C 补类型化成果和验收；D 合并设置/记录等长尾所有权；E 做全旅程回归和候选构建。默认入口切换已由后续授权先行完成，不替代上述验收。保留已有能力不等于永远保留重复实现。
